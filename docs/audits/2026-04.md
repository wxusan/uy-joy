# UyJoy — Deep Audit Report
**Date:** 29 April 2026
**Scope:** Full-stack audit (security, code, UX, performance, business, ops)
**Codebase root:** `/Users/xusan/Projects/uy-joy`
**Stack:** Next.js 14.2.35 (App Router), Prisma 5 + PostgreSQL, NextAuth (credentials), next-intl, Cloudinary, MapLibre, PostHog, Gemini AI, Tailwind.

> Read this once, then jump to **Section B (Critical Issues)** and **Section K (Roadmap)**. The single most important sentence in the document: **almost every API route and every server-rendered admin page is publicly accessible right now.** The "secret" `/portal/management-x7k9` URL is not protecting anything except the login form. Fix that this week or do not put this site in front of a real client.

---

## A. Executive Summary

**The good.** The visual design language on the homepage and `/kvartiralar` is genuinely premium — the Cormorant + Plus Jakarta pairing, the warm `#c66348/#15120f` palette, the aerial-spotlight hero in `ProjectTopView.tsx`, and the `LocationInfrastructure` map all feel like a real luxury developer site. The polygon-based building → floor → apartment flow is the right product mental model and the admin polygon editor is unusually sophisticated for a project of this size. ISR + `unstable_cache` + Cloudinary transformation helpers show the team thinking about performance. The data model (Project / Building / Floor / Unit / Lead) is sensible.

**The bad.** This is currently an unauthenticated CRUD app dressed up as a marketing site. Anyone on the internet can:

1. `GET /api/leads` → list every lead's name + phone (`src/app/api/leads/route.ts:5–26`).
2. `GET /api/units` → get `customerName`, `customerPhone`, `customerNotes` of every reserved/sold buyer (`src/app/api/units/route.ts:47–59` returns the full Prisma model).
3. `GET /portal/management-x7k9/leads` → server-renders all leads in HTML (`src/app/portal/management-x7k9/leads/page.tsx` does no `getServerSession` check; only the client-side `AdminGuard` redirects).
4. `POST /api/leads` (no rate-limit, no captcha, no validation) → spam the CRM.
5. `POST /api/projects`, `PUT /api/units/[id]`, `DELETE /api/buildings/[id]`, `POST /api/floors/[id]/copy-to-all` → mutate or wipe the public site's content.
6. `POST /api/upload` → upload arbitrary files (including SVG, which can carry script) into the project's Cloudinary account.
7. `POST /api/ai/translate` and `POST /api/ai/detect-floors` → burn the Gemini API key and trigger SSRF (the route `fetch()`es any URL the caller supplies).

**The PII leak you cannot afford.** The public homepage (`src/app/page.tsx`) feeds `getCachedProject()` (`src/lib/cached-queries.ts:6–23`) into `<ExploreClient project={JSON.parse(JSON.stringify(project))} />`. That Prisma query has no `select`, so the **entire** Unit model is serialized into the page payload — including `customerName`, `customerPhone`, `customerNotes` for every reserved/sold apartment. The TypeScript prop type is narrower, but TypeScript does not strip fields at runtime. Right now your homepage HTML contains the phone numbers of every customer who reserved a unit. This is a GDPR-equivalent breach under Uzbek personal data law (PD Law 547-IV) and must be fixed before any launch.

**The biggest opportunities.**
- A 1-hour change (server-side auth check + `select`-narrowed queries) eliminates the bulk of the security findings.
- The buyer flow is genuinely good — small CTA + form polish in `ContactForm` and `IntentPopup` plus a captcha will lift conversion noticeably.
- Removing four duplicate "Explore" entry points (`/projects/[id]`, `/projects/[id]/explore`, `/vizual`, `/`) would drop ~25% of the route surface and clarify the funnel.
- Image strategy is half-built: Cloudinary helpers exist but `FloorPlanPolygon` uses raw `<img>`, and `ProjectTopView` uses `unoptimized`. Wiring these consistently will visibly improve mobile load.

## B. Critical Issues (fix this week)

### B1. Admin pages have no server-side authentication
**Files:** `src/app/portal/management-x7k9/layout.tsx:9–40`, every server page under `src/app/portal/management-x7k9/**/page.tsx` (e.g. `leads/page.tsx`, `projects/page.tsx`, `projects/[projectId]/units/page.tsx`, `page.tsx`).

`AdminGuard` is a `"use client"` component that redirects after hydration. By that time Next.js has already executed the server `page.tsx` (which queries Prisma) and shipped the rendered HTML to the client. `curl https://yoursite/portal/management-x7k9/leads` returns the leads in the HTML body. Same for `/dashboard` (root admin page leaks `recentLeads` in `src/app/portal/management-x7k9/page.tsx:35–47`) and `/projects/[id]/units` (leaks `customerPhone` in HTML, `units/page.tsx:21–48`).

**Fix:** add server-side `getServerSession(authOptions)` at the top of every admin server page (or in `layout.tsx` if you make the layout an async server component) and `redirect("/portal/management-x7k9/login")` if no session. Better: do it in middleware so it covers the whole tree (see B2).

### B2. Middleware does not enforce auth on `/portal` or `/api`
**File:** `src/middleware.ts:55–60`. Matcher explicitly excludes `api`. There is no auth logic in middleware — only locale cookie writing. The "secret" path `management-x7k9` is security-through-obscurity (and it's already in your repo and `next-auth` `pages.signIn`, so it's not even secret).

**Fix:** add a second middleware path that requires a valid `next-auth` JWT for `/portal/management-x7k9/(.*)` (except `/login`) and for `/api/(projects|buildings|floors|units|leads|hero-images|faqs|users|upload|ai)/.*` POST/PUT/DELETE/PATCH.

### B3. `GET /api/leads` is unauthenticated — full CRM dump
**File:** `src/app/api/leads/route.ts:5–26`. No auth check. Pagination caps at 100 per call but anyone can iterate.

**Risk:** all lead names + phone numbers exfiltrate-able, plus `notes` and `assignedTo`. Direct competitor harm + privacy violation.

**Fix:** require admin session, or split into `POST` (public, validated) and `GET` (admin only).

### B4. Customer reservation PII shipped to every public page
**Files:** `src/lib/cached-queries.ts:6–23`, `src/app/page.tsx:51–113`, `src/components/ExploreClient.tsx:122` (`JSON.parse(JSON.stringify(project))`), `src/app/kvartiralar/page.tsx:38–49`, `src/app/vizual/page.tsx:51–58`, `src/app/projects/[projectId]/explore/page.tsx:38–43`.

`prisma.unit` includes `customerName`, `customerPhone`, `customerNotes`, `statusChangedAt`. None of the public pages `select` only safe fields, and serialization to the client preserves them. View-source on the homepage today contains buyer phone numbers.

**Fix:** rewrite `getCachedProject()` and the equivalent in `kvartiralar/page.tsx`, `vizual/page.tsx`, `projects/[projectId]/explore/page.tsx`, `projects/[projectId]/page.tsx` to use an explicit `select` that only returns: `id, unitNumber, rooms, area, status, pricePerM2, totalPrice, polygonData, labelX, labelY, sketchImage, sketchImage2..4, descriptionTranslations, features`. Same for the `/api/units` GET endpoint when no admin session is present.

### B5. `POST /api/upload` accepts arbitrary uploads with no auth and allows SVG
**File:** `src/app/api/upload/route.ts:11–53`. No session check. Allowed types include `image/svg+xml` (`line 23`). SVG can contain inline `<script>` and is served from your Cloudinary domain — an attacker could embed XSS payloads that run when the SVG is opened directly. There is no max-size limit (could be used to spam Cloudinary cost / your bandwidth).

**Fix:** require admin session; drop SVG (or upload SVGs through `cloudinary.uploader.upload` with `flags: "sanitize"` and serve via `f_jpg` transform); enforce `file.size < 10_000_000`; randomise/namespace `public_id`.

### B6. `POST /api/floors/[id]/copy-to-all` is unauthenticated and destructive
**File:** `src/app/api/floors/[id]/copy-to-all/route.ts:5–76`. Anyone can call this and **delete every unit on every other floor in a building** (`prisma.unit.deleteMany` at line 29) and overwrite their `floorPlanImage`. There is no transaction, so a partial failure leaves the building in an inconsistent state. Resets all `status` to `"available"`, silently nuking reservations.

**Fix:** require admin session; wrap whole loop in `prisma.$transaction`; warn the admin in the UI that statuses will be reset; add a confirm dialog with the count of units about to be destroyed.

### B7. SSRF in `/api/ai/detect-floors`
**File:** `src/app/api/ai/detect-floors/route.ts:35–40`. The route `fetch()`es whatever URL the caller passes in `imageUrl`. With no auth, anyone can use your server to hit internal endpoints (cloud metadata IPs `169.254.169.254`, internal DBs, etc.) and proxy the response into the Gemini call (or out via error logs).

**Fix:** require admin session; allow-list `res.cloudinary.com` (and any local `/uploads/...`); strip any URL that resolves to private/loopback IP space; cap `Content-Length`.

### B8. AI routes burn the Gemini key with no auth or rate limit
**Files:** `src/app/api/ai/translate/route.ts`, `src/app/api/ai/detect-floors/route.ts`, `src/app/api/ai/detect-apartments/route.ts`. None check session.

**Risk:** anyone can send unlimited requests until your Gemini quota / billing trips. Translate is especially attractive because it accepts arbitrary text.

**Fix:** require admin session + per-IP rate limit (Upstash Redis or `Vercel KV`).

### B9. Lead form has no rate limiting, no captcha, no validation
**Files:** `src/app/api/leads/route.ts:29–61`, `src/components/ContactForm.tsx`, `IntentPopup.tsx`, `FloatingContact.tsx`.

`POST /api/leads` accepts whatever you give it. `name` and `phone` are not sanitised, length-checked, or pattern-checked. A bot can flood your CRM with 10k fake leads in minutes. `IntentPopup` even sets `projectId: "N/A"` which is a string Prisma will happily store.

**Fix:** Zod or hand-rolled schema (`name` 1–100 chars, `phone` matches `/^[\+\d\s\-()]{6,20}$/`); per-IP rate limit (3/min, 30/day); honeypot field; reject `projectId` strings that are not valid cuids.

### B10. NextAuth secret may not be set in prod
**File:** `src/lib/auth.ts:57`. `secret: process.env.NEXTAUTH_SECRET` — fine if set, but I see no validation that it exists at boot. If it's missing in prod, NextAuth uses a dev key and JWTs are forgeable.

**Fix:** boot-time guard (`if (!process.env.NEXTAUTH_SECRET) throw new Error(...)`); rotate the secret if it has ever been committed.

### B11. CSRF is wide-open on mutating routes
None of the API routes verify origin or use a CSRF token. NextAuth's session cookie is `SameSite=lax` by default, which protects against most cross-origin POSTs, but `lax` still allows top-level navigations to trigger `GET`. Once you add server-side auth (B1), make sure the cookie is `SameSite=lax` (or stricter) and ideally check `origin`/`referer` on `POST/PUT/DELETE`.

## C. High Priority Improvements

### C1. Two contact widgets compete with each other
`src/components/FloatingContact.tsx` (LifeBuoy bottom-right) and `src/components/IntentPopup.tsx` (emerald button bottom-left + auto-popup at 33s / scroll 70% / mouse-leave) both render on every public page. The IntentPopup is registered… nowhere I can find — it is not imported in `layout.tsx`. Either it's dead code or it's rendered somewhere I missed; either way, ship one and delete the other. The FloatingContact is the better one (matches the brand palette, premium feel). The Intent popup uses a different design language (`bg-navy-900`, emerald, rounded-3xl, hardcoded Uzbek strings) and breaks visual consistency.

### C2. Hardcoded strings everywhere — multilingual claim is partially false
- `src/components/IntentPopup.tsx`: every string is hardcoded Uzbek (`"Xonalar soni"`, `"Yopish"`, etc., lines 155–225).
- `src/components/FloorPlanPolygon.tsx:165–183`: `"Xonadonlar hali belgilanmagan"`, `"Available/Reserved/Sold"` legend.
- `src/lib/utils.ts:1–15`: `formatPrice` returns `"mlrd" / "mln" / "ming"` regardless of locale.
- `src/app/portal/management-x7k9/page.tsx:8–17`: `LEAD_STATUS_LABEL` is English-only despite `getTranslations` available.
- `src/app/projects/[projectId]/page.tsx`: hardcoded English ("About the Complex", "Find Your Perfect Apartment", "Underground parking & 24/7 security").
- `src/components/LocationInfrastructure.tsx:23–54`: a parallel `copy` object reimplements i18n outside next-intl.
- `src/components/Footer.tsx`: phone number and Telegram handle are hardcoded literals duplicated in `ContactForm` and `FloatingContact`.

The user-visible result: switching to RU or EN leaves Uzbek words on screen. Decide on one source of truth (next-intl messages) and migrate all of it.

### C3. Duplicate "explore" pages
There are at minimum four ways to reach the building viewer: `/` (`src/app/page.tsx`), `/vizual` (`src/app/vizual/page.tsx`), `/projects/[projectId]` (`src/app/projects/[projectId]/page.tsx`), `/projects/[projectId]/explore` (`src/app/projects/[projectId]/explore/page.tsx`). The middle two use different hero designs, hardcoded English, and different cache/ISR settings. Delete `/projects/[projectId]` and `/projects/[projectId]/explore` outright — they look like prototypes left over from before the homepage was redesigned.

### C4. Public APIs return entire Prisma graphs
`/api/projects` returns every project, every building, every floor, every unit (full row). `/api/buildings`, `/api/floors`, `/api/units` (no `select`), `/api/floors/[id]` likewise. This is unnecessary network weight and a steady PII drip every time `customerPhone` is set.

**Fix:** narrow `select` on every public read; gate detailed reads behind the admin session.

### C5. `unstable_cache` invalidation has gaps
`revalidateTag("project")` is called in `units/[id]` PUT and `units` PATCH (good), but **not** in:
- `buildings/route.ts`, `buildings/[id]/route.ts` — building creates/updates/deletes don't invalidate.
- `floors/route.ts`, `floors/[id]/route.ts`, `floors/[id]/copy-to-all/route.ts` — floor mutations don't invalidate.
- `projects/[id]/route.ts` PUT — top-view image / coordinates change won't show up for 60s.
- `hero-images/*`, `faqs/*` — cached but not tag-invalidated; admins get a confusing "I just updated this, why doesn't the homepage show it" experience.

Pick a tag per concern (`project`, `hero-images`, `faqs`) and call `revalidateTag` after every write.

### C6. Inconsistent server-component boundaries
`src/app/portal/management-x7k9/layout.tsx` is a client component because of `SessionProvider` + `useSession`. That forces every admin page below it into a client subtree's session context, but the page files themselves are server components doing Prisma queries — which means `useSession()` cannot tell the page about the user before render. You currently work around this by querying without auth (B1), which is the actual root cause of the security holes. Pick a model: either (a) admin layout becomes a server component that calls `getServerSession`, redirects unauthenticated, and passes the user down via context, or (b) make every admin server page do its own `getServerSession` + redirect.

### C7. `floorPlanImage` is rendered with raw `<img>`
`src/components/FloorPlanPolygon.tsx:106–112` uses `<img src={floorPlanImage}>`. No Next/Image, no Cloudinary transform, no width/height (CLS), no `loading="lazy"`. Switch to `<Image>` with `getCardImageUrl()` and explicit dimensions.

### C8. `Content-Security-Policy` is not set
No CSP, no `X-Frame-Options`, no `Referrer-Policy`. With Cloudinary, MapLibre tiles, and PostHog all being external, a strict-but-functional CSP is non-trivial but is worth doing before launch (helps mitigate the SVG-XSS path in B5 even if you don't drop SVG).

### C9. Lead source string mismatch
`ContactForm` sends `source: "bosh-sahifa"`, `IntentPopup` sends `"intent_popup"`, `FloatingContact` sends `"floating_matchmaker"`, `UnitDetailModal` sends `"vizual"`. The admin labels in `LeadsClient.tsx:42–46` only know `"kvartiralar" | "vizual" | "bosh-sahifa"`, so 50% of your incoming leads will display as the raw key. Define an enum (TS type + DB CHECK / Prisma enum) and use it everywhere.

### C10. `IntentPopup` is "registered" but invisible
I cannot find it imported. If you removed it from `layout.tsx` but kept the file, mark it dead. If you intend to ship it, it conflicts with `FloatingContact` (C1), uses a different palette, and pushes a hardcoded UZ-only flow.

### C11. Footer columns link to dead pages
`src/components/Footer.tsx:25–35` lists `t("news")`, `t("careers")`, `t("paymentOptions")`, `t("documents")`, `t("visitResidence")` with no `href` (or a hash to `#contact`). Trust-killer for a real-estate site. Either remove the columns or wire them up.

### C12. `ProjectTopView` uses `unoptimized` `<Image>`
`src/components/ProjectTopView.tsx:152–163` — the hero image is the largest LCP element and you've explicitly turned off the optimizer. Cloudinary is fine to leave optimization on (set `loader` if needed); do not ship `unoptimized` for the hero.

## D. Medium Priority Improvements

### D1. Type safety
Many `any` casts in API routes (`buildings/[id]/route.ts:20`, `buildings/route.ts:8`, `units/route.ts:12,95`, `hero-images/[id]/route.ts`). The session role checks cast `(session.user as any).role` everywhere — define a NextAuth module augmentation in `src/types/next-auth.d.ts` so `session.user.role` is typed.

### D2. Status as string
`Unit.status`, `Lead.status` are `String` in Prisma. Use Prisma enums (`enum UnitStatus { available reserved sold }`, `enum LeadStatus { new inCRM ... }`). The `LEAD_STATUSES` array in `LeadsClient.tsx:22–25` already implies the contract; just lift it into the schema.

### D3. Translations stored as JSON strings, not relations
`Project.nameTranslations` is `String?` containing JSON. That works but you can't query "give me projects whose Russian name contains X". Two cleaner options: (a) split into `nameUz/nameRu/nameEn` columns (you already do this for `FAQ`, so it'd be consistent), or (b) `Json` type so Prisma at least parses it server-side. The current "JSON-in-string" pattern means every read goes through `try { JSON.parse } catch { … }` (`src/lib/translations.ts:22–42`).

### D4. `Unit.unitNumber` "auto-pad" logic is duplicated
`UnitDetailModal.getDisplayNumber`, `FloorPlanPolygon.getDisplayNumber`, `ApartmentDetailModal` (likely), and `FeaturedApartments.getDisplayNumber` each reimplement the same regex (`/^\d{1,2}$/`). Move to `src/lib/utils.ts`.

### D5. `formatPrice` is locale-broken
`src/lib/utils.ts:1–15` always returns Uzbek units and uses `ru-RU` for separators. `FeaturedApartments.formatPrice` reimplements it differently with `" UZS"` suffix and space separators. Pick one signature `formatPrice(amount, locale)` and route everything through it. Also: do you actually want to display prices in UZS only, or also USD? Real-estate buyers in Uzbekistan compare both.

### D6. Cookie locale detection runs on every page render
Middleware sets the cookie if missing (`src/middleware.ts:42–50`); page components and `LocationInfrastructure.tsx:130–132` re-parse `document.cookie` client-side; `i18n.ts` reads via `cookies()` server-side. Centralise in one helper. Also, the `?lang=…` query-param fallback common on multilingual sites is missing — direct sharing of a Russian apartment listing won't preserve language.

### D7. No pagination on `/api/projects`, `/api/buildings`, `/api/floors`, `/api/units` (default mode)
For a single complex this is fine, but if this is going to become a multi-project platform (your DB schema implies yes), you'll regret returning the entire graph in one shot.

### D8. Map style hard-codes Carto tiles
`src/components/LocationInfrastructure.tsx:170–197` — using `*.basemaps.cartocdn.com` raster tiles. Carto's free tier allows 75k tile requests/month; you'll blow through that with even modest traffic. Either self-host MBTiles, switch to `tile.openstreetmap.org` (CC, attribution required), or use MapTiler/Stadia with an API key.

### D9. `ScrollReveal`, `AnimatedCounter`, etc. are all client-only and ship JS for every section
For a homepage this isn't huge, but the ScrollReveal wrapper is used 8+ times and pulls a small IntersectionObserver setup each. Use one component with `Suspense` boundaries or migrate to CSS `@keyframes` triggered via `prefers-reduced-motion`-aware `view-timeline` (still progressive, no JS).

### D10. `puppeteer` is in dependencies but unused (?)
`package.json` lists `puppeteer ^24` and `@neondatabase/serverless`, `@libsql/client`, `@prisma/adapter-libsql` — none of which appear in source. The Prisma datasource is plain `postgresql`. Either you're planning Neon for prod (then remove libsql) or you're carrying ~150MB of dev deps for nothing. `puppeteer` alone bloats the build by an enormous amount.

### D11. Database-side defaults / constraints missing
- `Unit.status`, `Lead.status` should have a CHECK constraint or enum.
- `Project.expectedYear`: no range check; admin can save year `99999`.
- `Building.sortOrder`: no unique constraint within a project.
- `HeroImage`: max 3 enforced in app code (`hero-images/route.ts:23–28`) but not in DB. Two concurrent admins can race past it.
- `FAQ.isActive` defaults to `true` and there's no soft-delete; deletion cascades irreversibly.
- `latitude/longitude` are `Float?`, not bounded. A typo (`-2222`) breaks the map silently.

### D12. Cascade deletes are aggressive
`Building -> floors -> units` cascade is fine in theory, but right now an unauthenticated DELETE on `/api/buildings/[id]` annihilates the entire building's history, including units that have customers attached. Add a confirmation flow that requires you to first move customers/leads off, plus a soft-delete (`deletedAt`).

### D13. `/api/users` POST does not validate password strength
`src/app/api/users/route.ts:24–25` hashes whatever string you send. There's no minimum length, complexity, or "password breach" check. For an admin login, require ≥10 chars and ideally a passphrase.

### D14. `Lead.unitId` is a free-form string, not a relation
Schema has `Lead.unitId String?` but no FK. When the unit is deleted, the lead points at nothing and the admin sees `unitNumber` from a denormalized snapshot. Either make it a real FK with `onDelete: SetNull`, or document the snapshot intent in the schema.

### D15. Hero number is one phone number across the whole app
`+998 77 041 12 22` is duplicated in `ContactForm.tsx:112, 119`, `FloatingContact.tsx:9`, `Footer.tsx:5`, multiple placeholders. Move to `src/lib/contact.ts` and read from env (`NEXT_PUBLIC_SALES_PHONE`).

## E. Low Priority / Polish

- The `BuildingViewer` "back" button is conditional on `project.buildings.length > 1` (`ExploreClient.tsx:230`) — when there's only one building you fall through to `() => {}`, leaving a back button that does nothing. Hide it instead.
- `ApartmentDetailModal` and `UnitDetailModal` look duplicated; `GroupedApartmentModal` and `GroupedApartmentCard` ditto. Consolidate.
- `getBuildingLetter()` (`ProjectTopView.tsx:110–113`) returns the first 1–2 chars after stripping `"Block"`/`"Building"` — translates badly when the project uses Cyrillic names ("Блок А" → "БЛ"). Take only the localized building suffix.
- `IntentPopup.tsx` triggers PostHog event before the dialog opens and after success — no event for "dismissed at step 1 vs step 2", which is the most useful funnel signal.
- No `robots.txt`, no `sitemap.xml`, no Open Graph image, no Twitter card. Title is the generic `"UyJoy — Interactive Apartment Platform"` (`src/app/layout.tsx:35–38`) — should include the project name and city.
- `Plus_Jakarta_Sans` and `DM_Sans` are loaded with all weights 400–800; you only use 4–5 weights in practice. Trim weights and `subsets` to reduce font payload.
- `JetBrains_Mono` is loaded but I cannot find a usage — check, drop if so.
- The `vizual` route name is Uzbek transliteration; combined with `kvartiralar` and `projects/[id]/explore` it makes the URL space inconsistent. Pick one language for paths.
- Numerous mid-page `<a href="#contact">` anchors don't update the URL on iOS Safari without `scroll-behavior: smooth` set on `html`.
- The "Available/Reserved/Sold" legend in `FloorPlanPolygon.tsx` is hardcoded English even when the rest of the modal is translated.

## G. Architecture Review

**Can this scale?** For a single residential complex with up to ~10 buildings × 30 floors × 20 units (≈6,000 units) and a few hundred leads/month, the current architecture is fine. ISR + `unstable_cache` + Cloudinary will handle real traffic easily. Prisma + Postgres is comfortably below limits.

**Where it breaks down:**
1. **Multi-project ambition.** Schema supports `Project[]` and the URL space hints at it (`/projects/[id]/...`), but the homepage uses `findFirst()` (`cached-queries.ts:8`) and `kvartiralar` likewise. Decide: is this single-project-forever (then drop the per-project routes) or multi-project (then the homepage needs a project picker, the cache needs per-project tags, and the admin needs a project-scoped session).
2. **API surface vs. RSC.** The codebase is half RSC-with-Prisma (server pages do their own queries) and half SPA-with-/api (client components fetch JSON). Pick a primary mode. For an internal admin, server actions or one tRPC-style layer would deduplicate the eight near-identical route handlers I read.
3. **Admin layout is a client component.** This is the root of the auth problems (B1). Refactor: make `layout.tsx` a server component that calls `getServerSession`, then export a small `<SessionProviderShell>` client component for the bits that need React Query / `useSession`. Same conceptual fix as Section C6.
4. **No service layer.** Business rules ("when status flips to reserved, set `statusChangedAt` and clear `customerName` if going back to available") live duplicated across `/api/units/[id] PUT` and `UnitsClient.handleStatusChange`. Extract a `units.service.ts` (or domain functions) that both the API and any future server action call.
5. **Caching invalidation is coupled to writes.** The current `revalidateTag` calls live in some routes and not others (C5). Centralize: an `afterWrite(entity)` helper called by every mutation.
6. **Folder structure.** `components/admin/` is good. But generic `components/` mixes public and shared widgets. Recommend `components/(public|admin|shared)/` or move public marketing components into `app/_components/` colocated with their pages.

**Suggested architecture (only changes I'd actually make):**

- Server-component `layout.tsx` → `getServerSession` → redirect or pass user via prop.
- `lib/auth-guard.ts` exporting `requireAdmin()` for API routes (one-line at the top of each handler).
- `lib/dto/` with `unitToPublicDto(unit)` etc. — the only thing that ever reaches the browser.
- `lib/services/` for unit/lead/project mutations.
- `middleware.ts` enforces auth on `/portal/*` and `/api/*` (except `/api/leads POST` and `/api/auth/*`).
- Replace `cached-queries.ts` with one DTO-aware reader per page.

You don't need a rewrite — these are surgical changes.

No payment plan info or mortgage partners. No "About us" beyond a single section heading. For a residence at the price point implied by Cormorant/UZS millions, buyers expect: the developer's full company name, license number, photo of the construction, contact details of a specific sales manager (not just `+998 77 041 12 22`), and an option to schedule a viewing.

## I. Performance Review

### Initial load wins (already in place)
- ISR with `revalidate = 60` on `/`, `/kvartiralar`, `/vizual` is correct.
- `unstable_cache` over Prisma queries.
- Cloudinary `f_auto`/`q_auto` helpers.
- `dynamic(() => import('./ApartmentDetailModal'), { ssr: false })` in `FeaturedApartments`.
- MapLibre is only imported inside `LocationInfrastructure.useEffect` (lazy).

### Wins still on the table
1. **`unoptimized` Image in hero** (`ProjectTopView.tsx:156`) — drop it.
2. **Raw `<img>` in `FloorPlanPolygon`** (C7) — switch to next/image with explicit width/height to remove CLS.
3. **`JSON.parse(JSON.stringify(project))` ships full Prisma graph** — narrowing fields will cut payload by 40–60% on apartment-heavy projects. Each unit currently carries `customerNotes`, `descriptionTranslations`, and four sketch URLs; on a 200-unit complex this is meaningful.
4. **PostHog `autocapture: true`** with `capture_pageview` AND `capture_pageleave` — autocapture sends every click/input. On a long-form contact form, that's a lot of events. Disable autocapture and instrument explicit events; `capture_pageview` is also already done in `PostHogProvider.tsx:18–22`, so you're double-firing.
5. **`Plus_Jakarta_Sans` weights 400/500/600/700/800** — pick three; each weight is ~20–30 KB.
6. **`puppeteer` dependency** — if not used, removing it cuts install size enormously and avoids accidental shipping in serverless functions. Check the build for it.
7. **`/api/projects` cascading include** — for a fully-loaded project this is multiple round-trips Prisma flattens. With 6,000+ units it'll get slow. Split queries (one for project, one paginated for units, separate for buildings) and cache them independently.
8. **MapLibre style is fetched every page load** — set `localStorage` cache or precompose the style JSON.
9. **`.maplibre-gl.css` imported globally in `layout.tsx`** — only the `LocationInfrastructure` page uses MapLibre. Move the CSS import to the component.
10. **Animations.** `ProjectTopView`'s 3.1s `setInterval` fires on every page that includes it, even when off-screen. Pause when `document.hidden` or via `IntersectionObserver`.
11. **Re-render risks.** `ExploreClient` keeps `selectedUnit: any` and reconstructs handlers on every render; not a real issue at this size, but add `useCallback` for the click handlers if the apartment list grows past 200.
12. **Database queries.** `getCachedProject` `findFirst` with deep includes runs at most once per 60s under cache, so it's fine. But `prisma.unit.findMany` without `select` (used in `/api/units` and admin units page) reads ~30 columns per row; narrow it.

### Mobile-specific
- The CSS `aspect-[16/9]` hero on `/` is enormous on small phones; consider `aspect-[3/4]` or `[5/6]` below `md:`.
- Maplibre interactivity is disabled (`interactive: false`) — good for performance, but on mobile users tap and nothing happens. Add a "Open in Google Maps" overlay (you already have `mapUrl`).

## J. Business / Product Review

### What the homepage does well for conversion
- Clear "explore the building" hook above the fold. Matches buyer mental model.
- Real-time inventory counters (Available/Reserved/Sold) are a strong urgency device.
- Phone + Telegram + visit office + weekday hours all visible — three contact paths.
- ISR + caching keeps it fast for first-time visitors who often bounce.

### What hurts conversion
1. **Trust deficits.** No developer name, no license, no construction photos, no team, no past projects, no reviews. For a residence purchase (lifetime decision), this is fatal at scale. **Fix: dedicated /about page with developer info, license, gallery of past projects.**
2. **Confusing routes.** `/projects/[id]`, `/projects/[id]/explore`, `/vizual`, `/kvartiralar` — buyers shared a `/projects/abc123/explore` link will land on a different-looking, English-only page that diverges from your brand. Fold these into `/`.
3. **Lead form friction.** Contact form requires name + phone, which is fine. But the modal lead form (`UnitDetailModal`) is on a different palette and looks like a popup ad. Buyers in Uzbekistan are wary of "give us your number" modals — make the form less aggressive: use a small inline button "Request a callback for №[unit]" that expands inline, not a modal that occludes the apartment image.
4. **No pricing transparency.** The unit modal doesn't show the price. `formatPrice` exists but is not rendered in `UnitDetailModal`. Buyers want to see "from 850,000,000 UZS" / per-m² rate / monthly payment. Show price prominently on the modal and on each polygon hover (the legend already implies this).
5. **No payment plan / mortgage info.** Real estate sites in Uzbekistan win conversion by offering "0% boshlang'ich badal", "Ipoteka", monthly payment calculators. None of that here.
6. **The "Recommended" / `FeaturedApartments` section is generic.** It doesn't actually recommend — it shows whatever has polygons. Either drop the framing ("Featured apartments") or build a real recommender (filter by status=available, sort by view popularity, group by `rooms`).
7. **No floor / building comparison view.** Buyers compare 2-3 candidates. Add a "shortlist" that they can build by tapping ♥ on apartments, and an inline compare table. Most of your competition doesn't have this either, so it's a differentiator.
8. **Lead source attribution exists** (`source` field) but admin doesn't visualize per-source conversion. Add a tiny chart on the dashboard.
9. **Phone-only contact.** Add WhatsApp (very widely used in UZ). The Telegram link is good; WhatsApp needed for older buyers.
10. **No language at sign-up.** Buyers in Tashkent are split UZ/RU; you're defaulting to UZ via the cookie middleware (`middleware.ts:35`) but the `Accept-Language` heuristic falls through to UZ even when the browser is RU. Verify this logic; better to default to RU when the browser says RU.
11. **Localised number formatting** — Russian buyers expect spaces ("850 000 000"), not "850 mln" (`utils.ts`). The current rounding to "mln" / "ming" actually destroys the very precision (and trust) that high-ticket buyers want.

### Should building → floor → apartment be the main flow?
Yes, but only as one of two main flows:
- Master plan → Building → Floor → Apartment (current; great for visual buyers).
- Filter (rooms, area, price, availability) → Apartment list → Apartment (current `/kvartiralar`; great for spec-driven buyers).

Both should be reachable in two taps from the homepage. Today, the master-plan route is dominant and `/kvartiralar` is buried in the nav. Move it to the hero too: a tab switcher under the title — "Eng kerakli" (master plan) / "Hammasi" (catalogue).

### Metrics the business should track (PostHog already supports it)
- Funnel: `Viewed Block` → `Viewed Floor` → `Viewed Apartment` → `Contacted Sales`.
- Drop-off rate per step.
- Lead-to-meeting conversion (admin needs a status: meeting scheduled).
- Source attribution: master plan vs. catalogue vs. intent popup vs. floating widget.
- Time on `LocationInfrastructure` (proxy for "do they care about location?").
- Phone clicks (`tel:` href is currently not tracked — wrap `<a href="tel:">` in `posthog.capture("Phone Click")`).
- Telegram clicks (also untracked).
- Per-unit popularity (already implied, but plot it on the admin dashboard so sales know which apartments to push).
- Repeat visits (PostHog `person_profiles: identified_only`, but you never `posthog.identify`, so you'll only ever have anonymous distinct IDs).

### What to remove
- `IntentPopup` (kill it; `FloatingContact` does the same job, on-brand).
- `/projects/[id]` and `/projects/[id]/explore` (dead routes).
- The duplicated `Footer` columns that link to `#contact` (looks padded).
- The clip-art emoji "About the Complex" gallery in `/projects/[id]` (already off-brand).

### What to add
- Trust strip (license, completion year, developer name) in the hero.
- WhatsApp button in `FloatingContact`.
- Mortgage/payment-plan calculator (one of the highest ROI features for UZ real estate).
- Construction progress section with monthly photos + completion percentage.
- "Schedule a visit" calendar (Cal.com or Calendly embed).
- Admin: per-source funnel chart; per-unit view count; "this lead has been waiting 3 days, follow up" notification.
